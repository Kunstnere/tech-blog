我一直想有一个真正属于自己的技术博客。

不是社交平台上的一个账号，也不是某个内容系统里的一个页面，而是一个可以长期维护、随时迁移、完全掌握内容和代码的地方。

这篇文章记录我的选择和搭建过程。它既是一个开始，也是这个博客的第一篇工程笔记。

## 先想清楚：为什么要写博客

写博客最直接的好处是可以公开记录，但比“被更多人看到”更重要的是，它会强迫我把一件模糊的事情讲清楚。

一个开发任务完成以后，我可能知道代码能运行，却未必能解释：

- 为什么最终选择了这个方案；
- 这个方案在哪类场景下会失效；
- 哪些步骤只是当时碰巧有效；
- 如果重新做一次，哪些地方可以简化。

把这些内容写下来，相当于给未来的自己留一份带上下文的说明书。

因此，我给这个博客定了一个简单的原则：

> 不做资料搬运工，只记录真实发生的问题、验证过的过程和可以复用的判断。

## 为什么没有直接使用现成平台

现成平台最大的优势是开始得快。注册账号，点几下按钮，就可以发布文章。

但我在意三件事：

1. **内容要能带走。** 文章应该是一份普通的 Markdown 文件，而不是只能存在于某个平台数据库里的数据。
2. **网站要能长期维护。** 即使几年后更换框架，也不需要重新录入全部文章。
3. **页面要足够轻。** 博客的主要价值是阅读，不需要加载大量不必要的脚本。

所以最终方案是：

```text
文章：Markdown
框架：Astro
代码托管：GitHub
网站部署：Cloudflare Pages
域名：自己的独立域名
```

这套组合的分工很清楚：Markdown 保存内容，Astro 把内容生成静态网页，GitHub 保存版本，Cloudflare Pages 负责发布。

## 为什么选择 Astro

Astro 最适合我当前需求的一点是：默认生成静态 HTML，页面不需要为了展示文章而加载一整套前端运行时。

它同时满足了几件事：

- 用 Markdown 写文章，专注内容；
- 需要时可以加入 Astro 组件和少量 JavaScript；
- 构建结果是普通静态文件，不绑定特定服务器；
- 对 SEO、RSS、站点地图等基础能力支持比较直接。

Hugo 也是很好的选择，构建速度更快；WordPress 的编辑体验更成熟。但如果目标是“以写作为主，同时保留前端控制能力”，Astro 对我更合适。

## 博客的基本结构

一个博客看起来有很多页面，核心结构其实很简单：

```text
访问首页
  ├─ 读取全部公开文章
  ├─ 按发布时间倒序排列
  └─ 显示标题、简介、日期和标签

打开文章详情
  ├─ 找到 Markdown 文件
  ├─ 渲染正文
  └─ 生成固定网址

推送代码到 GitHub
  └─ Cloudflare Pages 自动构建并发布
```

这也是静态博客容易维护的原因：没有数据库，没有在线后台，没有需要长期关注的服务器进程。

## 发布一篇文章的流程

以后每写一篇新文章，只需要重复以下步骤：

1. 在 `src/content/blog/` 中新建 Markdown 文件；
2. 填写标题、简介、发布日期和标签；
3. 用 Markdown 写正文；
4. 在本地预览并检查排版；
5. 提交到 Git 并推送到 GitHub；
6. Cloudflare Pages 自动部署新版本。

文章发布以后，标题、摘要、文章列表、标签页和 RSS 都会从同一份 Markdown 内容生成。

## 下一步

第一版博客不会追求功能完整。先确保它具备最基本的能力：

- 能稳定发布文章；
- 阅读体验足够好；
- 内容由自己保存；
- 网站可以持续迭代。

接下来要做的事情也很明确：继续解决问题，保留上下文，然后把值得复用的部分写下来。

网站会被重新设计很多次，但一篇篇真实的技术记录会一直积累。这才是博客最重要的部分。
